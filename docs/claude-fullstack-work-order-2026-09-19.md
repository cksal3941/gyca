# Claude 후속 작업 지시서 — 접수·결제 출시까지 통합 구현

작성: Codex · 2026-09-19 · 기준: `mid-checkin-2026-09-19.md`와 현재 작업 트리

## 0. 요청과 담당 범위

사용자는 10월 초까지 주최 측이 직접 공모를 등록하고 참가자가 작품을 접수·결제할 수 있는 플랫폼을 원한다. Codex 사용량을 줄이기 위해 **Claude가 프런트 연결뿐 아니라 남은 백엔드 보완, 테스트, 배포 준비까지 주도**해 주세요. Codex의 매 단계 확인을 기다리지 않고 아래 순서로 진행합니다.

이 문서는 이전 `docs/claude-work-order.md`의 역할 제한을 이번 인계 범위에서 대체합니다. 기존의 “공통 계약·서버는 Codex만 수정”, “심사 백엔드는 설계 후 Codex 대기”, “checkout API 없음” 지침을 현재 작업의 차단 사유로 삼지 마세요. 이미 구현된 서버는 재사용하고 실제 결함·누락만 보완합니다. 이 문서는 구현 요청이며 운영 결제 개방이나 유료 서비스 신청 완료를 의미하지 않습니다.

Claude가 담당할 수 있는 범위:

- 기존 화면·디자인 유지, 실제 API 어댑터와 관리자 운영 화면 완성.
- `src/contracts/**`, `src/server/**`, `src/app/api/**`의 필요한 수정과 추가. 계약 변경 시 호출부·테스트·문서를 함께 반영.
- migration, 개발 데이터·계정 준비 도구, 통합 테스트, 빌드·컨테이너·배포 준비.
- PG 연동 조사·구현, 테스트 환경 검증, 계정 준비 후 실제 환경 연결.
- 후순위 CMS 확장과 운영 기능 구현.

Codex에게 남겨야 할 상시 구현 업무는 없습니다. 필요할 때 결제·권한·마감 동시성처럼 위험이 큰 변경의 독립 검토만 요청할 수 있습니다. 사용자에게 필요한 것은 사업자·PG 계약, 서비스 계정 준비, 실제 운영 정책과 자료의 확정입니다. 그 외 코드·테스트 작업을 사용자에게 대신 수행하도록 넘기지 마세요.

동일 작업 트리에 다른 작업자의 변경이 있으므로 먼저 상태를 읽고 기존 변경을 보존합니다. 이관 뒤 Codex와 같은 파일을 동시에 수정하지 않도록 이 문서의 단계별 진행표를 기준으로 소유권을 기록합니다.

현재 브랜치는 `frontend/live-api-wiring`이다. 중간 점검의 PR #1·커밋·원격 상태는 Claude의 보고이며, 이번 인계에서는 원격 상태를 다시 검증하지 않았다. 시작 시 현재 상태를 확인한다.

검증 범위를 구분해 보고한다. Claude의 로컬 PGlite+브라우저 결과는 프런트 성공·실패 흐름의 일부 증거이고, Codex의 269개 테스트는 로컬 서버 회귀 증거다. 둘을 합쳐 실제 PostgreSQL·S3·PG·운영 부하까지 검증했다고 표현하지 않는다.

## 3. 단계 1 — 공유 파일과 재현 가능한 작업 기반 확보

**우선순위 P0. 다음 UI 작업의 기반이며 즉시 시작.**

1. `git status --short`, 현재 브랜치, 추적 파일과 untracked 목록을 확인한다. 계약·서버·migration·스크립트·프런트 공통 의존성을 파일 단위로 목록화한다.
2. `.env*` 실제 비밀 설정, 로컬 DB, 브라우저 프로필, `.pnpm-store`, 에이전트 개인 설정은 커밋 대상에서 제외한다. `.env.example`은 실제 비밀값이 없는지 확인한다.
3. 기존 프런트가 공통 계약에 이미 의존하므로 필요한 공통 파일과 서버 파일을 함께 재현할 수 있는 통합 커밋 구성을 만든다. 변경을 되돌리는 reset/clean/stash나 master 전환으로 현재 작업을 잃지 않는다. `git add .`로 일괄 처리하지 말고 확인한 경로를 명시한다.
4. 공통 기반 → 서버/migration → 프런트 연결 순으로 검토 가능한 커밋으로 정리한다. 현재 브랜치에서 정리가 가능하면 과거 커밋을 강제로 재작성하지 않는다. 원격 게시·병합은 해당 세션의 기존 사용자 승인 범위를 따른다.
5. 임시 worktree 또는 별도 로컬 체크아웃에서 lockfile 기반 설치·타입 검사·서버 검증·빌드를 실행한다. 원래 작업 폴더의 미추적 파일이 없어도 성공해야 한다.
6. 전체 타입 검사를 먼저 실행하고, B-2가 다시 발생할 때만 Zod 스키마 실제 타입을 조사한다. `any`, `@ts-ignore`, 검사 대상 제외로 해결하지 않는다.

완료 기준: 클린 체크아웃에서 import 누락 없음, 모든 필요한 파일 추적됨, 실제 실행 명령·종료 코드 기록. 이 단계의 결과는 `docs/claude-integration-progress.md`에 누적한다.

## 4. 단계 2 — 재사용 가능한 로컬 운영자·심사 테스트 환경

**우선순위 P0. 권한이 없어 계속 403만 보는 상태를 해소.**

1. 임시 로컬 DB를 만들고 기존 인증 migration과 `scripts/lib/platform-migrations.mjs`의 전체 목록을 적용한다. PGlite 소켓 환경은 재현 가능한 시작/종료 명령으로 정리한다.
2. 실제 Better Auth 경로로 테스트 참가자·운영자·심사위원 계정을 만든다. 테스트 전용 이메일 확인과 역할 준비가 필요한 fixture는 운영 연결과 확실히 분리한다.
3. 운영자 권한은 `scripts/manage-organizer.mjs`와 `docs/backend/organizer-access.md`의 계정 대조·미리보기·감사 흐름을 재사용한다. 공모별 결제 권한은 `manage-payment-access.mjs`로 따로 다룬다. 심사위원은 기존 관리자 `/admin/judges`와 배정 API로 준비한다.
4. seed 도구는 개발 전용 opt-in, 로컬 대상 확인, production 거부를 적용한다. 현재 `scripts/seed-leipzig-dev.mjs`는 DATABASE_URL만으로 쓰기를 진행하므로 운영 DB 오사용 방어를 보완한다. 임의 접속 문자열에 자동 관리자 권한을 부여하지 않는다.
5. 계정/fixture 준비 도구 자체를 테스트한다. 로컬 fixture로 생성한 결제·운영 증거를 실결제 확인 자료로 사용하지 않는다. 실행 환경의 자동 승인 거절이 있으면 우회하지 않고 대상·사유를 기록하고 독립 작업을 계속한다.

완료 기준: 한 명령 또는 문서의 짧은 절차로 개발 DB·계정을 재현하고, 운영자 성공 응답과 일반 참가자 403, 권한 회수 후 거부를 실제 세션으로 확인한다.

## 5. 단계 3 — 주최 측 공모 등록과 접수 상세 운영 화면

**우선순위 P0. “우리 측에서 공모전을 올릴 수 있어야 한다”는 필수 요구.**

### 3-A. 관리자 상세와 CSV

1. `src/lib/api/ops.ts`에 실제 GET `/admin/competitions/{competitionId}/entries/{entryId}` 연결. 목록→상세 이동에 공모 ID를 보존하고 직접 접속에도 복원되도록 URL 구조를 정리한다. UUID·slug를 임의 혼용하지 않는다.
2. `AdminEntryDetailSchema` 기준으로 `files.displayName`, `guardianVerificationStatus`, `audit.type/actorId/occurredAt`, 인증서 상태를 표시한다. actorId를 알 수 없는 사람 이름으로 꾸미지 않는다. 이력은 최대 100건 요약임을 반영한다.
3. 동의 전문 `/consents`와 보호자 `/guardian-consents`를 별도로 연결한다. 보호자 수동 검증은 최신 API의 revision·증거 참조를 요구하고, 이메일 수락만으로 verified로 표시하지 않는다.
4. POST `/admin/competitions/{competitionId}/entries/export`를 현재 검색·필터·정렬 전체 조건으로 호출한다. CSV 성공은 JSON이 아닌 Blob, 오류는 JSON이다. 페이지 cursor·화면에 있는 행만으로 파일을 재생성하지 않는다. 개인정보 포함 안내와 다운로드 실패 처리, object URL 정리를 구현한다.
5. 서버에서 허용하지 않은 상세 액션은 숨기거나 사유를 표시한다. 접수 상세의 allowedActions를 공모 전체의 발표 권한처럼 사용하지 않는다. 관리자에게 참가자 전용 파일 다운로드를 우회 사용시키지 않는다. 필요한 관리자 파일 열람 API가 없다면 별도 권한·감사·서명 URL 계약을 추가하고 검증한다.

### 3-B. 공모 등록·정책·오픈 관리

1. GET/POST `/admin/competitions`, GET/PATCH `/admin/competitions/{competitionId}`의 실제 라우트와 스키마를 확인해 등록·편집 화면을 만든다.
2. 공모 제목·EN/KO 내용·기간·시간대·최소 단위 참가비·부문·연령·폼·업로드 규격·요강·승인된 전시 정보를 입력한다. 운영 값의 기본값을 새로 확정하지 않는다. 일정은 저장 시 UTC, 화면은 공모 시간대를 명시한다.
3. `/submission-policy`, `/payment-policy`, `/retention-policy`와 정책 이력 API를 연결한다. 참가 규정/개인정보/작품 이용허락을 별도 버전 문서로 유지한다. 보호자 연령 정책·확인 방식과 파일 보관 기간은 승인된 값만 입력한다.
4. `published`와 실제 접수/결제 활성화를 구분해 표시한다. `/launch-readiness`의 체크 결과와 차단 사유, `/launch-verifications`, `/open-applications`, `/pause-applications`, `/resume-applications`를 기존 계약대로 연결한다.
5. 외부 검증 증거가 없는 상태에서는 “준비 중”을 유지한다. 운영자가 테스트 fixture나 임의 체크박스로 storage/retention/live_payment_verification을 충족한 것처럼 만들지 않는다.
6. readiness/허용 작업이 계약에 부족한 운영 액션은 서버에서 추가 판단하도록 최소 확장하고 클라이언트와 함께 테스트한다. 서버 규칙을 프런트에서 별도로 재구현하지 않는다.

참조: `competition-admin-implementation.md`, `submission-policy-admin.md`, `payment-policy-admin.md`, `retention-policy.md`, `launch-control.md`, `admin-entry-detail.md`, `entry-export.md`.

완료 기준: 운영자가 공모를 등록·공개·수정하고 미완료 정책을 확인할 수 있음. 실제 오픈 조건 미충족 시 열리지 않음. 일반 계정·다른 공모·오래된 revision·재전송·잘못된 Origin을 검증.

## 6. 단계 4 — 참가자 흐름과 결제창 연동 완성

**우선순위 P0. PG 계정·통화 확인은 단계 1 착수 시 함께 시작해 기다리는 시간을 줄인다.**

### 4-A. 계정 없이 바로 가능한 작업

1. 공모 목록·홈 Apply·상세 Apply가 모두 실제 공모 응답을 사용하게 점검한다. 로컬 상수의 “접수 중”으로 접수 가능 여부를 판단하지 않는다. 비공개/마감/미준비 공모와 목록 페이지네이션을 확인한다.
2. 접수 저장·새로고침 복원·업로드·3종 동의·보호자 요청·제출 흐름에서 아직 mock가 섞이는 부분을 제거한다. live API 실패를 mock 성공으로 대체하지 않는다.
3. 미저장 입력, 파일 검증 중, 보호자 대기, 제출 완료, 결제 대기, 결제 확인 중, 접수 확정을 구분한다. `submitted ≠ received`, `payment succeeded ≠ receipt issued`를 유지한다.
4. `POST /orders/{id}/checkout`에 `{}`를 보내는 어댑터와 `PaymentCheckoutSessionSchema` 파싱을 연결한다. 스키마는 `src/contracts`에서 검색해 실제 위치를 사용한다. `start_payment`가 없으면 PG 이동을 시도하지 않는다.
5. 서버 redirect 세션을 처리하되 반환 URL 도착으로 성공 표시하지 않는다. 기존 confirm/reconcile 경계, 응답 유실·브라우저 닫기·재접속·지연 확정을 처리한다. 같은 결제 시도 재시도에는 동일 멱등키를 유지한다.
6. `src/server/payments`의 공급자 인터페이스와 기존 Toss 승인·조회·웹훅·환불 구현을 읽는다. 미구현 `beginCheckout`과 test-only runtime을 구분한다. 가짜 공급자는 테스트 주입에만 사용한다.

### 4-B. PG 선택과 구현

1. 사용자의 기존 선호는 Toss 계열 해외 결제다. 기존 문서는 EUR 지원을 확인하지 못해 막아 두었다. **현재 가맹 사업자 국가, 해외 발급 카드/국가 지원, 청구·정산 통화, 환불, 결제 방식**을 최신 PG 공식 문서와 실제 계약 조건으로 확인한다.
2. 문서에 적힌 KRW/USD/EUR 지원 설명을 최신 사실로 무조건 재사용하지 않는다. 조사 날짜·공식 출처·서면 확인 필요 항목을 `docs/payment-provider-decision.md`에 기록한다.
3. €70 → 7000 amountMinor 계약을 지원되지 않는 PG에 강제로 보내지 않는다. 결제 통화 변경이나 별도 국제 공급자 도입은 비용·표시·환불 영향과 함께 사용자에게 선택안을 제시한다. 임의 환율 계산이나 사업자 국가 추정으로 결정하지 않는다.
4. PG가 SDK 방식이면 기존 hosted redirect 계약에 맞추기 위해 존재하지 않는 URL을 만들지 않는다. 필요하면 checkout 응답을 방식별 union으로 확장하고 계약·프런트·서버·테스트를 함께 변경한다. 비밀 키는 서버에만 둔다.
5. 국내/해외 경로는 서버가 동결 참가자 국가·가맹점 지원 범위·승인된 정책으로 판정한다. 지원되는 경로만 안내하고, 해외 카드 거절을 접수 성공으로 숨기지 않는다.
6. 확인된 공급자의 결제 시작→승인/조회→검증된 원장→접수 확정→환불을 연결한다. 테스트 키와 운영 키 구분, 가맹점·주문·금액·통화 대조, 중복 이벤트·지연 웹훅·중복 청구 감지와 복구를 유지한다.

완료 기준: 계정 없는 단계는 계약·어댑터·로컬 통합 테스트 완료로 보고. PG 준비 후에는 sandbox 실제 결제창과 승인/조회/취소 증거를 남긴다. 운영 오픈은 별도 승인된 실검증까지 충족해야 한다. PG 미정 하나로 관리자·CMS·테스트 전체를 중단하지 않는다.

참조: `payment-checkout.md`, `toss-adapter-implementation.md`, `payment-api-implementation.md`, `payment-options-implementation.md`, `routed-orders-implementation.md`, `payment-recovery-implementation.md`, `refunds.md`.

## 7. 단계 5 — 결제 운영·대시보드·참가자 보조 기능

**우선순위 P0: 접수 기간 운영에 필요한 결제 확인/복구/환불. 나머지는 P1.**

1. GET `/admin/dashboard`를 연결한다. 승인액은 환불 전 총승인액이며 정산 매출로 부르지 않는다. 통화가 다른 금액을 더하지 않는다.
2. 공모별 `/payment-reviews`, `/payments/{orderId}`, `/payment-health`, 검토 이력과 복구 재큐잉을 연결한다. 전역 organizer와 결제 viewer/operator의 권한은 다르다.
3. 지연 승인 접수 확정 `accept-late-payment`와 환불 API는 서버 allowedActions, 현재 검토 버전·사유·금액·actionId를 사용한다. 버튼 클릭을 최종 성공으로 처리하지 않고 원장을 재조회한다. 환불 응답이 불명확할 때 새 키로 다시 청구 취소하지 않는다.
4. `/receipt-deliveries`를 연결해 메일 실패와 접수 실패를 구분한다. 작업 토큰과 이메일 원문은 화면에 노출하지 않는다.
5. 마이페이지 인증서 목록·다운로드, 초안 철회, 본선 참가 의사 응답을 현재 API에 연결한다. 본선 confirmed는 유료 본선 참가비 납부 완료가 아니다. €1,100 주문을 임의 생성하지 않는다.
6. `/privacy/requests`와 관리자 `/admin/privacy-requests`를 연결한다. `approved_for_execution`을 “삭제 완료”로 표시하지 않는다. 실제 삭제 실행은 보관 정책에 맞춘 별도 후속 구현이며 결제·동의 증적을 무조건 지우지 않는다.
7. 개인정보 탭의 일반 프로필 수정은 기존 Better Auth `/settings`와 기능을 비교해 중복 구현을 피한다. 선택 홍보 동의는 현재 계약 지원 여부를 확인하고 빈 영역/미제공을 유지한다. 작품 이용허락과 합치거나 필수로 바꾸지 않는다.

참조: `admin-dashboard.md`, `payment-admin-implementation.md`, `payment-health.md`, `receipt-delivery-admin.md`, `privacy-requests.md`, `certificates.md`.

## 8. 단계 6 — 심사 운영·단계별 결과·인증서

**우선순위 P1. 접수·결제 오픈을 막는 작업보다 뒤에 진행하되 이미 있는 서버를 새로 만들지 않는다.**

1. `/admin/judges` 활성화/비활성화, 공모별 `/review-rubric`, `/judge-assignments` 생성·목록·회수·재배정 관리 화면을 연결한다.
2. 블라인드 작업자 결과 `/blind-asset`를 운영자가 검토한 뒤 `/approve`로 승인한다. PDF 메타데이터 삭제만으로 본문 이름까지 익명화됐다고 간주하지 않는다. 승인된 별도 파일만 심사위원에게 제공한다.
3. 기존 심사 화면의 실제 성공 흐름을 배정된 계정으로 검증한다. 미배정 접근, 배정 회수 직후 접근, revision 충돌, 누락 점수, 제출 후 잠금과 rubric에 따른 재수정 정책을 확인한다.
4. 관리자 `/entries/{entryId}/review`로 내부 결정을 기록하고 `/results/rounds/{official_selection|finalist}/publish`로 단계별 발표한다. **발표는 임의 체크된 행을 반복 처리하는 기능이 아니라 공모 전체/해당 라운드의 원자적 처리**다. mock의 bulkPublishResult 의미를 그대로 가져오지 않는다.
5. 결제 확인이 끝나지 않은 submitted 건, 미완료 심사, 마감 전, 누락 보관 정책 때문에 발표가 차단되는 경우를 UI에 설명한다. 상세 allowedActions만으로 공모 전체 발표 버튼을 추론하지 않는다.
6. `/certificates/issue`는 `{entryIds,stage,actionId}`와 실제 응답 스키마대로 연결한다. 202/pending은 예약, issued만 발급 완료다. 부분 성공 여부도 서버 계약을 확인하고 mock의 BulkOutcome으로 바꾸지 않는다.
7. 인증서 공식 서식·로고·서명·문구 승인을 받기 전에는 운영 발급 작업자를 켜지 않는다. 이름·작품명에 악센트/다국어 글자가 있는 경우 현재 PDF 글꼴의 한계를 검증하고 필요하면 적절한 폰트를 포함한다.

완료 기준: 로컬 계정으로 심사·발표·인증서 예약 흐름 검증, 실제 S3 준비 후 PDF 승인·다운로드 성공 확인. 공개 전 내부 결정은 참가자 응답에 드러나지 않음.

## 9. 단계 7 — 공개 CMS와 완료 프로젝트 아카이브

**우선순위 P1. 첫 출시의 사실성은 필수, 모든 CMS 확장은 접수·결제 완성 뒤.**

1. 기존 editorial CMS(`/content/editorial`, `/admin/content/editorial`)로 공지·일정·FAQ·News·Press를 연결한다. body는 일반 텍스트이며 raw HTML로 넣지 않는다. 초안·보관 문서는 공개하지 않는다.
2. 기존 partner CMS(`/content/partners`, `/admin/content/partners`)를 연결한다. 관계 확인 증거·사유→확인→발행 흐름, 철회 시 비공개를 유지한다. `no-store` 응답을 프런트의 영구 캐시로 무력화하지 않는다.
3. Klimt Villa는 완료 프로젝트다. 기존 `src/lib/content/archive.ts`, `klimt-villa.ts`, `ProjectArchiveView`와 `docs/leipzig-klimt-content-and-cms.md`를 기반으로 서버 계약·migration·관리자·공개 API를 추가한다. migration 번호는 착수 시 공식 목록을 확인해 다음 번호를 사용한다. 적용된 기존 SQL을 수정하지 않는다.
4. 소개, 공모·선정 과정, 선정작, 전시 사진, 수여식 사진, 판매 사례, 구매자 인터뷰, 전시 인증서, 판매 인증서, 결과·실적의 10영역을 지원한다. 프로그램 종류가 달라도 동일한 구조를 재사용한다.
5. 각 영역은 자료 준비/공개 가능 상태와 실제 payload를 분리한다. 승인되지 않은 사진·실명·인터뷰·판매 금액·성과 수치를 만들지 않는다. 증거/공개 승인 참조는 관리자 전용으로 두고 공개 DTO에서 제거한다.
6. 실제 자료가 아직 없으면 명시적 준비 중 상태로 유지한다. 완료 프로젝트에 신규 접수 CTA를 넣지 않는다. 참가자 보관 파일을 그대로 공개 갤러리 파일로 바꾸지 않는다.
7. Exhibition/Performance/International/Winners 확장은 승인된 명칭·장소·미디어와 작품 이용허락을 서버에서 검증하도록 설계한다. CMS 표기용 날짜·금액이 접수 원장 정책을 덮지 않게 한다.

완료 기준: 준비되지 않은 자료는 공개 사실로 보이지 않음. 서버 공개 projection과 실제 브라우저를 둘 다 검증. 자료 수집 지연이 접수·결제 출시 작업을 막지 않음.

## 10. 단계 8 — 스테이징과 마감 직전 장애 검증

**우선순위 P0. 단계 3~5와 병행 준비하며 출시 전에 완료.**

1. 기존 Cloud Run/Supabase/S3/메일 구성 문서와 실제 준비 계정을 대조해 `docs/staging-readiness.md`에 서비스별 준비/미준비/담당/증거를 기록한다. 비밀값은 적지 않는다.
2. 계정이 없을 때도 환경변수 예제, 배포 점검, migration image/web image, CI 초안과 스케줄러 설정 파일은 준비한다. 유료 계정 개설·계약·실거래는 사용자의 구체적인 승인 범위에서 진행한다.
3. 실제 PostgreSQL에 인증+플랫폼 migration을 적용하고 `database-check.mjs`로 검사한다. 운영 대상이면 백업·복원·적용 순서와 실패 시 복구 계획을 먼저 갖춘다.
4. private/versioned S3, CORS, 정확한 버전 GET/DELETE, 브라우저 PUT, 만료 URL, 손상 PDF·20쪽 미만·크기 제한·중단/재시도를 검증한다. 현재 실제 업로드 검사 범위를 코드로 확인하고 지원하지 않는 영상·음원 형식을 UI에서 허용하지 않는다. 첫 공모에 필요하면 검사·용량·시간 제한까지 함께 확장한다.
5. 메일 확인/보호자 메일/접수 메일, 결제 복구, retention, 블라인드 파일, 인증서 작업자를 각각 설정·검증한다. 미사용 후순위 작업자는 비활성으로 남길 수 있지만 필수 접수·복구 작업은 실제 예약 실행이 필요하다.
6. `pnpm build --webpack`과 Docker runner/migration 이미지 빌드·기동을 검증한다. Webpack 성공이 Linux Docker 성공을 대신하지 않는다. Node 런타임은 현재 검사에 맞는 24 계열을 사용한다.
7. 실제 테스트 참가자의 가입→초안→업로드→동의→보호자 확인(대상자)→제출→PG 결제→received/접수번호→마이페이지→접수 메일을 실행한다. 해외 참가자·지원 국가·거절 카드·중도 이탈·환불도 별도 확인한다.
8. 실제 PostgreSQL에서 동시 재시도·웹훅 중복·마감 경계를 검증한다. PGlite의 단일 프로세스 테스트로 동시성 보장을 선언하지 않는다.

필수 장애 시나리오:

| 상황 | 확인할 결과 |
| --- | --- |
| 업로드 중 마감 또는 업로드 검증 지연 | 승인된 접수 성립 기준대로 처리하고 미접수를 접수 완료로 표시하지 않음 |
| 마감 직전 PG 승인, 웹훅은 마감 후 도착 | 설정된 시각 기준에 맞춰 복구, 중복 접수번호 없음 |
| 승인 요청 응답 유실/탭 종료/서버 재시작 | 같은 시도 확인·조회로 복구, 새 청구를 무조건 만들지 않음 |
| 결제는 성공, 접수 원장 저장 실패 | 내구성 있는 복구로 수렴, 운영 검토 대상 추적 가능 |
| 중복 웹훅·동시 confirm/reconcile | 접수번호·작업 예약이 정확히 한 번, 서로 다른 실제 청구는 이상 건으로 남김 |
| 결제 거절·지원하지 않는 카드 | 접수 미완료와 재시도 가능 조건을 명확히 안내 |
| 메일 실패 | received는 유지하고 발송 작업만 재시도 |
| 관리자가 접수 일시 중단 | 기존 submitted 건 결제 정책은 유지, 신규 접수만 의도대로 차단 |
| 부하 급증 | DB 풀·응답 지연·오류율·업로드/검사 처리량을 측정, 병목과 복구 확인 |

부하 목표는 예상 동시 참가자·파일 크기를 사용자에게 확인해 결정한다. 임의 수치의 테스트를 충분한 용량으로 단정하지 않는다. 테스트는 승인된 전용 환경에서 실행하고 실제 고객에게 메일·결제를 발생시키지 않는다.

## 11. 단계 9 — 출시 판단과 인계

1. 첫 오픈 필수 흐름과 미사용 후순위 기능을 목록으로 고정한다. 최소 출시 조건은 주최 측 공모 등록·정책·접수 운영, 참가자 저장/파일/동의/제출, 지원 PG 결제·접수 확정, 실패 복구·문의 추적이다.
2. 운영 정책과 실제 외부 검증 증거를 현재 revision에 등록하고 서버 launch-readiness를 확인한다. 테스트 결제 키, 이전 revision 증거, 만료 증거로 오픈하지 않는다.
3. 사용자에게 실제 스테이징 URL, 검증 결과, 남은 차단 사항과 운영 오픈할 공모·시점을 제시한다. 운영 공개 범위의 승인을 받은 뒤 기존 오픈 API로 처리한다.
4. 운영자 계정 권한, 공모 수정/중단/재개, 결제 예외·환불, 데이터 내보내기, 장애 연락과 복구 절차를 짧은 운영 문서로 제공한다.
5. 완료 여부는 “화면 완성”, “코드 테스트 통과”, “외부 서비스 실검증”, “운영 활성화”를 분리해 적는다. 실제 PG 미연결이면 결제 시스템 구축 완료로 보고하지 않는다.

## 12. 사용자에게 한 번에 정리해 받을 사항

아래 항목은 `docs/operator-decisions-needed.md`에 현재 근거·미확정값·필요 시점을 적어 한 번에 요청한다. 예전 답변으로 확인된 항목은 다시 묻지 않는다. 비밀번호/비밀 키를 채팅에 요청하지 않는다.

- 계약 사업자 국가·법인명, PG 신청/계약 상태, 원하는 청구·정산 통화, 해외 참가 국가 범위.
- 사용할 클라우드/DB/저장소/메일 계정 준비 여부와 관리자 초대 방식.
- 10월 초 정확한 목표일, 처음 오픈할 공모와 필수 분야·파일 형식.
- 제출 마감 시각·시간대·결제 유예·접수 성립 기준, 참가비와 환불 규정.
- 영문명/학년 필수 여부·연령 기준일·국가별 보호자 정책·확인 방식.
- 참가 규정/개인정보/작품 이용허락의 승인 문구·버전·공개 범위와 파일·증적 보관 기간.
- 전시 명칭·장소 승인, 사업자 표시 정보·고객지원 연락처·요강 PDF와 아카이브 실자료.

법적 문구·국가별 연령 기준은 동의 근거와 적용 조건을 검토한 운영 결정을 받는다. “유럽은 모두 16세”처럼 단순 규칙을 새로 확정하지 않는다. 응답 대기 중에도 어댑터·관리 화면·로컬 테스트·배포 준비는 진행한다.

## 13. 단계별 검증·보고 규칙

각 단계는 구현→관련 테스트→브라우저/서버 실제 동작 확인→기록 순으로 닫는다. 실패했거나 못 실행한 항목은 이유와 다음 해소 작업을 명시한다.

```powershell
node node_modules/typescript/bin/tsc --noEmit --incremental false

pnpm build --webpack
```
