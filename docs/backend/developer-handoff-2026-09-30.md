## 3. P0 — 실제 접수·결제를 열기 위한 작업

### B01. 결제창 시작·운영 PG 연결 — 미구현

**근거:** `src/server/payments/provider.ts`의 `beginCheckout`은 선택 인터페이스다. `toss.ts`의 실제 공급자 반환 객체에는 구현이 없다. `service.ts:240`과 `:248`에서 이 기능이 없으면 503을 반환한다. `configuredTossProvider`는 `tosspayments-test`만 허용하고 `liveMode:false`로 고정한다. 키를 입력하는 것만으로 운영 결제가 열리지 않는다.

작업:

1. 실제 계약 사업자·가맹점·청구 통화에 맞는 PG 제품과 결제창 방식을 결정한다. “토스 글로벌”이라는 명칭만으로 현 코드와의 호환성을 가정하지 않는다.
2. 공급자 결제창 시작 기능을 구현한다. 현재 계약은 HTTPS redirect 세션이다. 선택한 PG가 브라우저 SDK 방식을 요구하면 프런트와 checkout 계약부터 함께 조정한다.
3. test/live 설정과 가맹점·통화 검증을 구현하고 잘못된 조합은 활성화되지 않게 한다. 같은 공급자 구성이 주문·승인·웹훅·복구·환불·readiness에 일관되게 주입되어야 한다.
4. 성공/실패/취소 복귀와 서버 승인 검증을 연결한다. 브라우저의 성공 URL·금액을 접수 성립 근거로 쓰지 않는다.
5. 공급자 지원 국가·수단·환불 정책을 기존 payment routing에 등록한다. 현재 런타임은 공급자 1개를 주입하므로 국내/해외 2개 PG를 쓰면 공급자 선택 로직까지 확장한다.

완료 기준: 계약된 테스트 환경에서 결제창 시작→승인→received/접수번호→환불 통과. 동일 요청/웹훅 중복 시 이중 청구·접수번호 중복 없음. 운영 키 경로와 오픈 조건을 별도 확인하고 실제 소액 결제·환불 증거를 확보한다.

### B02. EUR 고정 계약과 가맹 통화 정합성 — 결정 + 구현

**근거:** `src/contracts/index.ts:46,116`, `src/server/payments/service.ts`, `toss.ts`에 EUR가 고정되어 있다. 참가비 최소단위 7000은 현재 EUR 계약에서 €70을 뜻한다.

작업: EUR 유지 가능 여부를 계약으로 확인한다. 다른 통화로 전환한다면 공통 타입·DB CHECK·금액 최소단위·주문 snapshot·PG 변환·환불·표시·테스트를 함께 수정한다. 통화 문자열만 치환하거나 임의 환율을 적용하지 않는다. 기존 주문 금액·통화는 소급 변경하지 않는다.

완료 기준: 지원 통화별 금액 단위, PG 전송값, 승인 응답, 원장, 환불액이 일치한다. 지원하지 않는 통화·국가에는 결제 시작 액션을 주지 않는다. 이 점검은 PG의 최신 상품 지원 여부를 외부에서 확인한 조사가 아니다.

### B03. 배포 이미지의 live 모드 설정 — 보완 필요

**근거:** `src/lib/api/mode.ts:14`는 `NEXT_PUBLIC_API_MODE`가 live가 아니면 mock을 사용한다. `.dockerignore`는 `.env*`를 제외하고, `Dockerfile` builder에는 이 변수를 전달하는 ARG/ENV 없이 `pnpm build --webpack`가 실행된다.

현재 Dockerfile을 별도 수정 없이 빌드하면 빌드 시 live 값이 없는 것이 문제다. 런타임에만 NEXT_PUBLIC 변수를 넣는 것으로 브라우저 번들에 반영된 모드를 교정할 수 없다.

작업: builder에서 live 모드를 명시하고 배포 전 검사에 포함한다. 시크릿은 빌드 인자로 넣지 않는다. 개발 시드·로컬 DB·mock이 운영 산출물에 섞이지 않도록 점검한다. Linux에서 standalone 이미지와 PDF/이미지 검사 의존성이 실제 기동하는지 확인한다.

완료 기준: 깨끗한 환경에서 이미지 빌드→기동→브라우저가 실제 `/api/v1`을 호출. DB/API가 실패하면 샘플이 아닌 오류 표시. 개발 공모·개인정보 fixture가 운영 DB에 없음.

### B04. S3 업로드·마감 처리 용량 — 연동·검증 + 보완 판단

**근거:** `src/server/uploads/s3.ts`, `service.ts`, `inspect.ts`. 비공개 버전 객체 업로드/다운로드 구현은 있다. 검사는 파일 전체를 읽어 worker thread에서 실행하며 인스턴스당 동시 2건·15초 제한이다. `MAX_UPLOAD_BYTES`는 64 MiB다. `complete`는 검사 후에도 접수 가능 상태를 다시 확인한다.

작업:

- 실제 버킷·versioning·공개 차단·CORS·업로드/읽기/삭제 최소 권한 구성.
- 업로드 PUT 성공 후 complete 실패·검사 용량 초과·재시도·연결 중단을 검증.
- ‘마감 전에 전송 완료했으나 검사 중 마감’의 인정 기준을 확정하고 현재 동작과 일치시킨다. 필요하면 수신시각 기록과 별도 비동기 검사 큐로 보완한다.
- 확정한 동시 접수 목표로 메모리·검사 지연·DB 풀을 측정하고, 2건 제한이 실제 병목이면 큐/작업자 분리를 구현한다.

완료 기준: 최대 규격 파일의 실제 브라우저 업로드→검사→제출 성공, 다른 계정 원본 접근 거절, 재전송 중복 방지, 마감 경계와 용량 초과 시 복구 가능한 안내. 프로토타입의 대용량 영상·음원 지원과 혼동하지 않는다(B15).

### B05. 보호자·메일 운영 준비 판정 — 보완 + 연동

**근거:** `guardian-runtime.ts`, `guardian-consent.ts`, `guardian-verification.ts`에 기능이 있고 `/guardian-consent` 페이지도 있다. 그러나 `src/server/competitions/launch-runtime.ts:14`는 `guardianVerificationConfigured:true`를 고정 전달한다. 이 값은 메일 발송·기능 플래그·담당자 확인 절차의 실제 준비를 보증하지 않는다.

작업:

- 필요한 국가의 정책과 메일 발신 도메인, HTTPS, guardian 플래그를 구성한다.
- 준비 상태를 ‘수동 확인 API 존재’와 ‘실제 보호자 접수 가능’로 구분하고 readiness가 이를 정확하게 반영하도록 한다.
- 참가자 요청→메일 수신→보호자 3종 동의→운영자 증거 확인→verified→제출의 브라우저 정상 흐름을 완주한다.
- 현재 요청은 DB에 저장한 뒤 메일을 보낸다. 메일 실패 시 요청 기록·분당/누적 제한이 남으므로 발송 상태·재시도/지원 절차를 보완한다. 토큰은 API 응답이나 로그에 노출하지 않는다.
- `guardian-consent.ts` 계약에 응답 스키마를 추가해 프런트의 임시 스키마(`src/lib/api/index.ts:632` 이후)와 통합한다.

완료 기준: 실제 메일 수신·만료·재발송·정책/revision 변경·동의 후 미검증 차단·운영자 확인 성공. 메일 실패와 기능 OFF가 정상 준비로 보이지 않음. 단순 이메일 수락을 보호자 신원 검증 완료로 표시하지 않음.

### B06. 주최 측 정책 입력·오픈 근거 등록 — 화면 연결

**근거:** submission-policy/payment-policy/retention-policy/launch-verifications API는 있으나 현재 `CompetitionEditor`는 LaunchControl·CompetitionForm·PresentationEditor로 구성된다. 프런트 API/컴포넌트에서 해당 정책·근거 등록 경로의 호출을 찾지 못했다.

작업: 3종 동의문 EN/KO와 버전, 보호자 국가표, 결제 경로·환불 안내, 보관 정책, 외부 검증 근거 입력 기능을 연결한다. 첫 오픈을 개발자가 설정한다면 서버 API를 사용하는 검증된 CLI/운영 절차를 먼저 제공해도 된다. 직접 SQL로 준비 플래그를 바꾸는 절차는 제공하지 않는다.

완료 기준: 신규 공모를 DB 수동 편집 없이 등록→정책 저장→revision에 맞는 실제 검증 근거 저장→canOpen→오픈. 프런트 Open 버튼은 서버 `canOpen/allowedActions`를 따르도록 검토한다(현재 LaunchControl은 checks로 allConfigured를 계산한다).

### B07. 실 PostgreSQL·작업자 스케줄·장애 관측 — 연동·검증

**근거:** `scripts/migrate-all.mjs`, `database-check.mjs`, `storage-check.mjs`, `run-scheduled-jobs.mjs`, `scripts/lib/scheduled-jobs.mjs`, Dockerfile와 배포 runbook이 있다. 저장소에서 자동 배포/스케줄 인프라 구성 및 실제 실행 증거는 확인하지 못했다.

작업:

- 운영/스테이징 DB 분리, TLS·풀·동시 연결 한도, 인증+001~039 migration, 백업과 복원 검증.
- payments / receipts / retention / blind-reviews / certificates 작업을 실행할 스케줄 등록. 각 토큰과 IAM 분리.
- 큐 지연·stalled·메일 실패·결제 검토 대상 경보와 담당자 지정. `payment_review` outbox는 생성되지만 receipt worker는 `entry_received`만 처리하므로 검토 알림/모니터링 경로를 별도로 완성한다.
- readiness 검증 기록은 실제 검증 후 저장한다. 테스트 경로가 운영 결제 검증을 대체하지 않는다.
- 마감 동시성·웹훅 중복/지연·작업자 중단/재실행·시크릿 교체·복구 훈련을 수행한다.

완료 기준: 새 환경에서 배포 재현, 외부 작업자 자동 실행, 장애 경보 수신과 복구, 백업 복원 결과를 증거로 남김. 관리형 서비스 계정과 PG 계약은 발주 측이 제공해야 한다.

## 4. P1 — 빠진 운영 기능과 미완료 흐름

### B08. 제출 후 미결제 접수 종료 — 미구현, 마감 전 필수

**근거:** Entry에 expired 상태는 있지만 `src/server`에서 해당 상태로 전환하는 경로를 찾지 못했다. `withdraw-draft.ts`는 미제출 초안만 철회한다. `result-admin.ts:179,234`는 submitted가 한 건이라도 있으면 결과 발표를 막는다. 결제 recovery는 공급자 상태 조회를 수행하며 접수 종료 기능이 아니다.

영향: 제출 후 주문을 만들지 않거나 결제를 포기한 건이 submitted로 남으면, 나머지 참가자의 심사가 끝나도 결과 발표가 막힐 수 있다. **코드 경로의 정적 분석 결과이며, 이 특정 장애 시나리오를 이번에 DB로 재현하지는 않았다.**

작업: 결제 유예 종료 후 미결제 확정/검토 중을 구분해 종료하는 작업자 또는 운영 API를 구현한다. 늦게 도착한 기한 내 승인·불명확 PG 응답과 경합할 때 금전 증거를 먼저 확인하고 원장/접수 상태를 원자적으로 처리한다. 만료된 접수의 보관/삭제 정책도 추가한다.

완료 기준: 주문 없는 submitted, 미승인 주문, 승인 응답 유실, 유예 안/밖 승인 각각의 종료·복구 테스트. 중복 실행 안전, 접수번호 중복 없음, 미결제 처리 후 결과 발표 가능. 단순 시간 경과만으로 실제 결제 성공을 삭제/무시하면 안 된다.

### B09. 환불 응답 유실 복구 — 보완 필요, 환불 개시 전 필수

**근거:** `src/server/payments/refunds.ts`는 요청을 pending으로 예약하고 같은 actionId 재시도를 지원한다. 독립 환불 조회/복구 작업자는 확인되지 않는다. `src/app/(site)/admin/payments/page.tsx:98`는 클릭할 때마다 새 actionId를 생성한다.

작업: 실패 응답 뒤 기존 환불 요청 ID를 보존해 재조회/재시도한다. PG 멱등키 보장 기간 이후에는 취소 요청을 맹목적으로 다시 보내지 않고 공급자 환불 내역과 대조한다. PG에서 확정 거절한 건과 응답 유실을 구별해 pending을 정리할 수 있는 근거·감사 경로를 구현한다.

완료 기준: 공급자는 환불했으나 응답 유실→원장 확정, 명확한 거절→정확한 종료, 부분환불 동시 요청, 총 환불액 한도, 동일 작업 중복 취소 없음. 현재 서버 단위/통합 테스트 통과를 실제 PG 환불 검증으로 대체하지 않는다.

### B10. 개인정보 삭제 실행·탈퇴 경로 통일 — 미구현 + 충돌 점검

**근거:** `src/contracts/privacy-requests.ts`의 최종 승인 상태는 approved_for_execution이며 completed 상태/실행 작업자가 없다. `src/lib/auth.ts:51`은 Better Auth 직접 계정 삭제를 활성화하고 `/settings`의 `authClient.deleteUser` 호출도 남아 있다.

작업: 승인 후 계정 접근 차단·세션 폐기·식별정보 익명화·작품/파생본/인증서 처리·법적 보관 예외·완료 증거까지 설계한다. 직접 deleteUser와 검토형 삭제 요청을 일원화하고 관계 데이터가 있는 계정/없는 계정/보관 보류 계정의 동작을 각각 확인한다.

이 점검은 직접 삭제가 모든 기록을 우회 삭제한다는 뜻이 아니다. FK와 불변 트리거로 실패할 가능성도 있어 실제 데이터로 확인해야 한다. 불변 증거 보호를 끄거나 CASCADE로 해결하지 않는다.

완료 기준: 승인·보관 보류·실행·실패 복구·완료의 추적 가능성, 중복 실행 안전, 삭제된 계정의 로그인 차단, 보관 대상 증거 유지와 노출 제한.

### B11. 파일·증거 보관 범위 완성 — 일부 미구현

**근거:** retention 정책에는 consentEvidence/paymentEvidence.retainDays가 있지만 서버에서 이를 집행하는 작업자는 찾지 못했다. 기존 asset deletion은 철회 초안/선정/미선정 원본 중심이다. `uploads/service.ts`의 remove는 removed_at만 설정하며 이 경로에서 삭제 job을 만들지 않는다.

작업: 방치 초안·업로드 만료/고아 객체·접수 중 교체/제거 파일·미결제 만료 건·블라인드 파생본·인증서·동의/결제 증거별 처리 범위와 예외를 명시하고 필요한 정리 작업자를 추가한다. 이미 구현된 원본 exact-version 삭제는 재사용한다. 백업에서의 보관/복원 시 재적용도 정한다.

완료 기준: 각 데이터 종류의 생성→보관기한→보류→삭제/익명화 이력 검증. 공개 아카이브 사본의 이용허락과 접수 원본 보관을 구분한다. 보관 일수는 계약·운영 관할에 맞는 입력값으로 받으며 이 문서는 법정 기간을 확정하지 않는다.

### B12. 관리자 심사·보호자 운영 연결 — 서버 구현, 화면 미연결

관리자 judges 화면은 심사위원 활성화·루브릭 중심이다. 현재 프런트에서 아래 API 호출을 확인하지 못했다. 백엔드 개발자는 기존 계약을 설명하고 Claude와 연결 범위를 나눈다.

- `.../entries/{id}/guardian-consents` 및 `.../{requestId}/verify`: 보호자 동의 전문·증거 확인.
- `.../judge-assignments`, `.../{assignmentId}/reassign`, `/revoke`: 배정·교체·회수.
- `.../{assignmentId}/blind-asset`, `/approve`: 파생본 상태 확인·블라인드 적합성 승인.
- 본선 참가 응답/운영자 확정 API의 운영 동선도 확인한다.

완료 기준: 운영자 화면에서 배정→블라인드 승인→심사위원 실제 열람/제출→결과 결정까지 수행. 보호자 수동 검증도 DB 직접 수정 없이 완료. 원본 개인정보가 심사 API에 포함되지 않음. 외부 검증 전 임의 verified/approved 처리를 하지 않는다.

### B13. 인증서·finalist 통합 검증 — 구현 존재, 보완/검증 필요

**근거:** `src/server/certificates/{service,pdf,worker}.ts`, `src/server/entries/result-admin.ts`. Claude 기록의 인증서 500은 빈 `{}` 제출 snapshot fixture에서 발생했다. 정상 제출 데이터로 재현하기 전에는 인증서 기능 전체가 고장났다고 단정하지 않는다.

작업:

- 실제 접수 API로 완전한 제출 snapshot을 만드는 fixture로 1차 발표→finalist→발급→S3 PDF→다운로드를 검증한다.
- 인증서는 participant.nameEn·englishTitle을 요구하고 `latinDisplay`와 Helvetica로 문자 범위가 제한된다. 첫 접수 폼의 이름 필수 여부와 발급 조건을 일치시키거나 폰트/문자 지원을 확장한다. 긴 이름·제목 줄바꿈/넘침도 검증한다.

완료 기준: 적격자만 발급, 재실행 시 중복 인증서 없음, 참가자 본인만 다운로드, 실제 PDF 표시 확인, finalist 공개 전 결과 비노출.

### B14. 비밀번호 복구·계정 메일 정상 흐름 — 화면/실서비스 미완료

**근거:** `password-reset-email.ts`는 `/reset-password#token` 링크를 생성하지만 현재 `src/app`에서 해당 페이지를 찾지 못했다. Better Auth 설정과 메일 adapter는 이미 있고 기능은 플래그로 제어된다.

작업: 비밀번호 찾기·재설정 페이지, 성공/만료/재사용 오류, 메일 인증 후 로그인 흐름을 연결한다. 관리자·일반 사용자 계정 복구도 실메일로 검증한다.

완료 기준: 실제 링크로 비밀번호 변경→기존 세션 폐기→새 비밀번호 로그인, 토큰 로그/URL query 노출 방지. 존재하지 않는 계정의 안내도 검토한다. 프런트 담당과 분담 가능하다.

## 5. P2 — 최초 구상 대비 확장 또는 운영 대안이 필요한 항목

### B15. 영상·음원·다장르 접수

현 코드는 표지 JPG/PNG 및 PDF, 최대 64 MiB 중심이다. launch-readiness form 검사도 필수 book_pdf(최소 20쪽)와 cover_image를 요구한다. 폼 편집 화면에서 항목을 바꿀 수 있다고 모든 장르가 지원되는 것은 아니다.

영상/음원을 첫 출시 범위에 포함하면 P0로 승격한다. MIME/규격, multipart·중단 재개 업로드, 검사·미디어 처리 작업자, 심사 플레이어, 블라인드 기준, 보관을 구현한다. 도서 공모전만 먼저 열면 명시적으로 후속 범위로 둔다.

### B16. 본선 추가 참가비·기관 단체접수

본선 state와 nullable orderId는 있으나 현재 결제 생성은 접수비 중심이며 본선 주문 생성·연결·자동 확정 흐름은 확인되지 않는다. 무료/수동 본선 확정 운영이면 기존 API를 쓸 수 있다. 유료 본선 참가, 기관 일괄접수·일괄결제가 필요하면 별도 작업으로 산정한다. 과거 작품 판매 실적 아카이브와 신규 작품 구매 결제는 다른 범위다.

### B17. 공개 미디어·추가 알림

CMS는 승인된 URL을 저장하는 구조이며 공개 이미지/PDF를 업로드·변환·보관하는 전용 관리자 미디어 API는 없다. 최초에는 운영자가 공개용 저장소에 등록한 URL을 입력할 수 있으나 비공개 접수 원본을 공개 버킷으로 전환하지 않는다.

Resend 메일은 계정 인증·비밀번호 재설정·보호자·접수 안내 중심이다. SMS, 심사/결과/인증서 발급 알림, 결제 검토 운영자 알림은 제품 요구를 확인해 추가한다. 마감/결제 장애 경보는 B07에서 우선 다룬다.

## 6. 반드시 유지할 계약과 구현 원칙

1. `entryStatus`, `reviewStatus`, `publishedResult` 3축을 합치지 않는다. submitted는 제출 내용 고정이고 received는 검증된 접수 확정이다. 접수번호는 received에서만 표시한다.
2. 금액은 정수 최소단위 amountMinor다. 통화별 최소단위와 PG 전송 단위를 명확히 분리한다.
3. 버튼은 서버 allowedActions/blockingReasons에 따른다. 브라우저 성공 화면이나 네트워크 200만으로 결제 성공을 만들어내지 않는다.
4. 제출 snapshot·동의문 버전·원장·감사 이력의 불변성을 유지한다. seed를 지우기 위해 불변 트리거를 끄지 않는다.
5. 원본·파생본·공개 사본을 구분하고 심사 블라인드는 API 응답에서 지킨다.
6. migration 001~039를 이미 적용한 환경이 있을 수 있다. 변경은 새 migration으로 추가하고 클린 설치와 기존 환경 업그레이드를 모두 검증한다.
7. 새 Next.js 코드는 저장소 AGENTS.md 및 설치된 `node_modules/next/dist/docs/`의 해당 가이드를 먼저 확인한다.
8. 비밀키·실참가자 정보는 문서/커밋/채팅에 넣지 않는다. 계정 접근 권한은 초대와 시크릿 저장소로 받는다.

## 7. 권장 인수·작업 순서

### 단계 A — 환경과 계약 확인

저장소/의존성/001~039/검증 명령을 재현한다. 기존 운영 DB 유무와 test/live 환경을 구분한다. 사업자·PG·통화 및 도서만 첫 출시할지 확인한다. 이 결정 뒤에 실제 일정·견적을 산정한다.

### 단계 B — 유료 접수 세로 흐름 완성

B01~B07을 진행한다. 신규 공모 생성부터 실제 참가자 가입→보호자 확인→파일 업로드→3종 동의→제출→주문→PG→received→접수 메일까지 단일 환경에서 완주한다. 브라우저 세션/권한을 사용하고 직접 DB로 received를 만드는 시드를 완료 증거로 쓰지 않는다.

### 단계 C — 장애와 마감 처리

B08~B11을 진행한다. PG 응답 유실·환불 pending·미결제 종료·동시 접수·메일 장애·파일 삭제 복구를 검증한다. 접수 시작 전 마련해야 할 대응 절차와 자동화 완료 일정을 명시한다.

### 단계 D — 심사·발표·인증서와 운영 인계

B12~B14를 진행한다. 배정→블라인드 승인→심사→1차/본선 발표→인증서까지 정상 데이터로 검증한다. 운영자 가이드와 장애 복구 명령을 인계한다. B15~B17은 첫 출시 포함 여부를 계약서에 명시한다.

- 사업자/법인 국가와 PG 가맹 정보, 허용 청구·정산 통화, 지원 카드/국가.
- 호스팅·PostgreSQL·S3·메일·도메인/DNS 계정의 작업 권한과 비용 담당.
- 참가비, 접수 시작/마감/시간대/결제 유예, 환불 규정, 예상 참가 건수·마감 집중 동시 사용자 목표.
- 3종 동의문·국가별 보호자 기준·보관 기준, 실제 전시 명칭/장소 승인, 요강과 인증서 문구.
- 공개 가능한 사진·수상작·인터뷰·인증서 사본과 이용 근거.

정해지지 않은 항목은 개발자가 입력 가능한 설정 구조와 검증 계획을 먼저 완성한다. 외부 계정이 없다는 이유로 fixtures·어댑터·테스트까지 미루지는 않는다.

### 기존 문서에서 수정해서 읽을 부분

- `docs/staging-readiness.md`의 ‘계정 확보 후 실행만 남음’은 B01~B03 등 코드 공백을 반영하지 못한다. 테스트키 경로만으로 live_payment 준비 완료가 되지 않는다.
- `docs/live-mock-remnants.md`의 카드/아카이브 공개 계약 부재는 현재 코드와 다르다. 카드·프로젝트·Winners·Exhibitions API와 연결 화면이 이미 있다.
- `docs/operator-decisions-needed.md`의 ‘입력 화면 완비’는 공모 기본 폼에 한정해서 읽는다. 정책/검증 근거 운영 도구는 B06을 확인한다.
- `docs/claude-integration-progress.md`의 위쪽 미착수 항목보다 아래쪽 후속/추가 검증 내용을 우선한다. 1차 결과 발표 성공과 finalist·인증서 미검증을 구분한다.
- 최초 회고의 ‘약 80%’는 인수 기준으로 쓰지 않는다. 이 문서의 기능별 완료 기준과 외부 검증 증거로 범위를 합의한다.
