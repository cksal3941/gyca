# 접수 도메인과 운영 정책 초안

## 기본 원칙

접수, 결제, 파일, 심사 결과를 서로 다른 상태로 저장한다. 화면은 이들을 조합해 설명하되 접수 완료를 추측하지 않는다. 모든 시각은 서버가 기록하고 UTC로 저장한다. 사용자에게는 공모 기준 시간대와 필요시 현지 시각을 함께 표시한다.

## 상태

| 영역 | 상태 | 의미 |
| --- | --- | --- |
| 접수 | `draft` | 편집 가능한 지원서 |
| 접수 | `submitted` | 필수 자료와 동의를 검증하고 제출 내용을 고정함. 아직 접수 완료는 아님 |
| 접수 | `received` | 정책상 유효한 제출과 검증된 결제로 접수 확정 |
| 접수 | `withdrawn` | 접수 철회. 환불 성공을 뜻하지 않음 |
| 접수 | `expired` | 정책상 접수 가능 기간 만료. 기록과 결제 증거는 보존 |
| 결제 시도 | `pending` | 승인 확인 전 |
| 결제 시도 | `succeeded` | 서버가 공급자의 승인 정보를 검증함 |
| 결제 시도 | `failed` / `cancelled` | 명시적인 실패 또는 취소 확인 |
| 결제 시도 | `expired` | 결제창 또는 시도 만료. 뒤늦은 승인 여부는 재확인 대상 |
| 환불 | `pending` / `succeeded` / `failed` | 원결제와 독립적인 환불 기록 |
| 파일 | `pending_upload` / `uploaded` / `validating` / `ready` / `rejected` | 전송과 검증 단계 분리 |
| 심사 | `not_started` / `under_review` / `completed` | 심사 진행 상태 |
| 결과 | `official_selection` / `finalist` / `not_selected` | 공개 시점이 지난 결과만 참가자 응답에 포함 |

미발표 결과는 참가자에게 `null`로 반환한다. 미발표 결과를 내려준 후 UI에서 숨기지 않는다. Official Selection 이후 Finalist 진출 이력을 잃지 않도록 결과 이력과 단계별 인증서를 보존한다.

결제와 접수 갱신 사이에 장애가 나면 `submitted` + 결제 성공 상태가 존재할 수 있다. 화면에는 접수 확인 중으로 표시하고 서버의 복구 작업이 확정한다. 이때 결제 재시도를 허용하지 않는다.

## 데이터 엔터티

| 엔터티 | 주요 필드 및 제약 |
| --- | --- |
| Competition | slug, 언어별 내용, 접수 기간, 기준 시간대, 비용·통화, 폼 버전, 정책 버전, 공개 여부 |
| Entry | 내부 ID, 소유 계정 ID, 공모 ID, 상태, revision, 작성 자료, 제출 시각, 접수 확정 시각, 접수번호 |
| SubmissionSnapshot | entry ID, 변경 불가능한 제출 내용, 파일 버전 목록, 동의 버전 목록, 생성 시각 |
| Asset | entry ID, 용도, 임의 저장소 키, 실제 크기·형식, 체크섬, 페이지 수, 검증 상태 |
| ConsentRecord | 제출 ID, 문서 ID·버전·언어, 동의 주체, 확인 방식, 서버 기록 시각 |
| Order | entry ID, 유형, 서버 산정 금액·통화, 결제 가능 종료 시각, 정책 버전 |
| PaymentAttempt | order ID, 공급자, 공급자 결제 ID, 상태, 검증된 승인 시각, 수신 시각 |
| Refund | payment ID, 금액, 사유, 상태, 공급자 참조 ID |
| ProviderEvent | 공급자 및 이벤트 ID 고유 제약, 수신 시각, 처리 상태, 재처리 이력 |
| ReviewAssignment / Review | 심사위원·작품 배정, 폼 버전, 점수·코멘트, revision, 제출 시각 |
| Result / Certificate | entry ID, 선정 단계, 공개 시각, 인증서 ID, 비공개 파일 참조, 발급 이력 |
| Outbox / AuditEvent | 재시도할 알림·후속 작업, 행위자·대상·행위·서버 시각 |

금액은 통화 최소 단위의 정수로 저장한다. EUR 70은 `amountMinor: 7000`, `currency: EUR`다. 브라우저가 보낸 가격은 신뢰하지 않는다. 다른 통화로 환산·청구하는 정책은 미확정이다.

결제 시도는 주문당 여러 개일 수 있다. 재시도 전에 기존 시도를 재확인하며, 늦은 중복 승인은 무시하지 않고 초과 결제로 기록해 운영 처리 대상으로 만든다. 환불 합계는 승인 금액을 넘지 못하며 동시 환불도 트랜잭션으로 제한한다.

## 주요 전이 및 불변 조건

1. 임시저장은 소유자와 revision을 검사한다. 같은 버전을 동시에 수정하면 한 요청만 성공한다.
2. 제출은 서버에서 필수 필드·자료 검증·동의·기간을 확인한 뒤 스냅샷을 생성한다. 실패하면 부분 제출을 남기지 않는다.
3. 제출 후 파일을 바꿔 이미 결제된 작품이 교체되지 않도록 한다. 재개방은 별도 정책과 이력이 필요하다.
4. 결제 주문은 고정된 제출 내용에 연결한다. 계정·금액·통화·주문 참조를 서버에서 검증한다.
5. 접수 확정과 접수번호 발급은 원자적으로 처리한다. 중복 이벤트가 번호와 알림을 중복 생성하지 않는다.
6. 승인 알림 순서가 뒤바뀌어도 성공한 결제를 과거 실패 이벤트로 덮어쓰지 않는다.
7. 접수 완료 이메일 실패는 접수 실패가 아니다. outbox를 통해 재시도한다.
8. 관리자·심사위원·참가자용 데이터 응답은 별도로 구성한다. 다운로드 요청마다 권한을 확인한다.

## 마감 정책에서 결정할 항목

DOCX에는 2026-12-31 23:59 KST가 기재되어 있다. 해당 분의 끝까지 허용한다면 배타적 종료 시각은 2027-01-01 00:00:00+09:00, UTC로 2026-12-31 15:00:00Z다. 이는 제안 해석이며 운영 확인 전 적용하지 않는다.

| 항목 | 결정 필요 내용 |
| --- | --- |
| 접수 성립 | 파일 제출과 결제가 모두 마감 전이어야 하는지 |
| 결제 유예 | 기한 내 제출자에게 별도 결제 기간을 줄지, 정확한 종료 시각 |
| 승인 기준 | 공급자 검증 승인 시각과 서버 수신 시각 중 판단 기준 |
| 지연 이벤트 | 이미 만료 처리된 주문의 기한 내 승인을 복구하는 규칙 |
| 검증 지연 | 기한 내 전송됐지만 PDF 검증이 뒤늦게 완료되는 경우 |
| 재제출 | 제출 후 수정, 불량 자료 교체, 마감 후 보정 허용 범위 |

미확정 정책은 설정에서 미확정으로 유지하고 실결제 접수 개시를 막는다. 프런트엔드는 서버의 `allowedActions` 및 `blockingReasons`에 따라 버튼을 표시한다.

## 파일 및 미성년자 데이터

- 저장소는 비공개를 기본으로 하며 짧은 유효기간의 업로드·다운로드 URL을 사용한다.
- 서버가 저장소의 객체 존재·크기·형식과 검증 결과를 확인해야 `ready`가 된다.
- PDF 파싱에는 시간·메모리·파일 크기 제한이 필요하다. 최소 20쪽 규칙은 서버에서 검증한다.
- 최대 용량, 암호화 PDF 허용 여부, 보호자 확인 방식, 연령 산정 기준일, 보관 기간은 미확정이다.
- 저작권·전시 이용허락·홍보 공개·개인정보 처리·보호자 확인은 버전별 증적으로 분리한다. 법적 문구나 국가별 적용 조건은 이 문서가 확정하지 않는다.
- PDF 본문·메타데이터·파일명에도 식별정보가 있을 수 있으므로 API 필드 제거만으로 블라인드를 보장하지 않는다.
- 계정 삭제 시 출품·결제 보관 및 익명화 정책을 정해야 한다. 기존 Better Auth의 계정 삭제 기능과 신규 엔터티 관계를 구현 전에 검토한다.

## 검증 시나리오

- 타인의 entry ID로 조회·수정·파일 발급을 시도하면 거부된다.
- 두 탭에서 같은 revision을 저장하면 한 요청은 충돌을 받는다.
- 미검증 파일 또는 누락된 필수 동의가 있으면 제출이 거부된다.
- 결제창 성공 리다이렉트만으로 접수가 확정되지 않는다.
- 동일 요청·웹훅 반복에도 접수번호와 성공 알림은 한 번만 생성된다.
- 금액·통화·주문 불일치는 접수 확정으로 이어지지 않는다.
- 마감 직전·정각·직후 및 지연 승인 시나리오를 확정된 정책대로 판정한다.
- 결제 성공 직후 서버 장애가 나도 재확인으로 접수가 복구된다.
- 미발표 결과와 배정 외 작품 정보가 API에 포함되지 않는다.
