# 결제 복구·접수 메일·파일 파기 스케줄러 실행

2026-09-16. 기존 내부 API를 호출하는 일회성 실행 도구다. 서버 배포·스케줄 등록·실제 PG 조회·이메일 발송은 수행하지 않았다.

## 실행

스케줄러 프로세스에 BETTER_AUTH_URL(실제 HTTPS origin), GYCA_JOB_KIND(payments, receipts, retention, blind-reviews 또는 certificates), GYCA_JOB_LIMIT(1~20, 기본 10)을 설정하고 아래 명령을 사용한다.

```sh
node scripts/run-scheduled-jobs.mjs
```

payments 작업에는 PAYMENT_RECOVERY_TOKEN, receipts 작업에는 RECEIPT_EMAIL_TOKEN, retention 작업에는 RETENTION_JOB_TOKEN이 필요하다. 서버와 같은 값이어야 하며 스케줄러에는 해당 작업 토큰만 제공한다. DB·S3·PG 비밀 키는 이 실행 도구에 필요하지 않다. 명령행 인자로 토큰을 넣지 않는다. 서버 쪽 기능 플래그와 공급자 설정은 별도로 준비되어 있어야 한다.

runner Docker 이미지에 파일을 포함했다. 이미지 기본 명령은 웹 서버이며, 스케줄러에서는 위 명령으로 덮어쓴다. Linux 이미지 빌드는 아직 확인하지 않았다. 외부 스케줄 서비스의 작업 등록과 주기는 스테이징 처리량을 확인한 뒤 설정한다.

## 처리 규칙

- 고정 경로로 JSON {} POST만 수행하며 리다이렉트를 따라가지 않는다.
- 한 번에 한 작업씩 최대 설정 건수까지 호출한다. 요청당 최대 30초, 응답 최대 8KiB다. 최대 설정 20건이면 네트워크 대기만 최장 약 10분이므로 스케줄러 실행 제한을 고려한다.
- idle이면 즉시 종료한다. 실행 자체가 같은 HTTP 요청을 자동 재시도하지 않는다. 다음 실행은 기존 서버의 작업 임대·재시도 상태를 따른다. 타임아웃이어도 서버 처리가 끝났을 수 있다.
- 출력은 processed, exhausted, stalled 집계뿐이다. processed는 호출로 처리한 작업 수이며 결제 성공 또는 메일 전달 수가 아니다. exhausted=true는 배치 한도에 도달했다는 뜻이며 미처리 건수는 모른다.
- stalled 작업 발견 시 종료 코드 1. HTTP/설정/응답 오류도 코드 1이며 그 지점에서 중단한다. retry_scheduled는 서버가 재시도를 예약했다는 의미로 정상 종료 대상이다. 개별 주문·메일의 상세 원인은 서버 기록에서 확인한다.
- 장기 실행 서버가 아니므로 호출 사이의 대기나 자체 스케줄 등록은 없다. 결제, 이메일, 파일 파기는 서로 다른 스케줄 작업으로 구성한다.

## 검증 및 남은 작업

주입한 전송 함수를 사용한 테스트에서 경로·작업별 토큰 선택, 빈 작업 종료, 상한, 잘못된 설정과 302/401/비정상 응답 거부, stalled 집계를 확인했다. 관련 ESLint 통과. 실제 HTTPS 통신·스케줄 서비스·장애 알림·메일/PG 공급자 연결은 검증하지 않았다. 이 도구 추가로 접수 오픈 조건은 변경되지 않는다.
