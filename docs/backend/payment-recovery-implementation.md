# 결제 재확인 작업 구현

2026-09-15. 서버 작업만 변경했다. 실제 PG 설정·DB 마이그레이션·배포·스케줄러 등록은 수행하지 않았다.

## 구현

- `007_payment_recovery.sql`: 재확인 대상, 시도 횟수, 다음 실행 시각, 작업 점유 토큰·만료 시각, 마지막 오류 코드 저장.
- `src/server/payments/recovery.ts`: 한 번 호출할 때 신규 대상 최대 50개 발견, 처리 대상 1개 점유·조회·상태 반영.
- `POST /api/internal/payments/reconcile`: 스케줄러용 내부 경로. body `{}`, 전용 Bearer 토큰 필수. 사용자 세션으로 호출하는 API가 아니다.

주문과 승인 요청 또는 결제 이벤트가 기록되어 있고, 성공·운영 검토 상태가 아닌 건을 찾는다. 결제를 시작하지 않은 단순 주문은 조회하지 않는다. 설정된 공급자·가맹점·테스트/라이브 범위만 처리한다. 제출 당시 결제 기한이 지났어도 조회할 수 있으며, 접수 확정 여부는 기존 원장의 판정 정책을 그대로 따른다.

작업은 공급자의 **조회 API만** 사용한다. 결제 승인·취소·재청구를 실행하지 않는다. 금액·통화·결제 결과를 추측하거나 만료시킨다고 간주하지 않는다.

## 중단·재시도

DB 행 잠금과 SKIP LOCKED로 다른 실행이 처리 중인 작업을 피한다. 외부 API 호출 중에는 DB 잠금을 보유하지 않는다. 120초 동안 완료되지 않은 작업은 다시 점유할 수 있다. 이전 실행은 고유 토큰이 달라졌다면 작업 상태를 덮어쓰지 못한다. 결제 원장 자체의 이벤트 중복 방지도 유지된다.

조회 오류 또는 미확정 결과는 30초부터 대기 시간을 늘려 최대 15분 간격으로 재시도한다. 실제 시작 시각은 스케줄러 호출 빈도에도 좌우된다. 최대 12회 후에는 stalled로 남기고 `payment_review` outbox 작업 한 개를 저장한다. 마지막 시도에서 프로세스가 중단된 경우도 점유 만료 후 stalled로 정리한다.

참가자의 직전 수동 조회로 429가 발생하면 10초 뒤로 미루며 시도 횟수를 소모하지 않는다. 오류는 공통 코드만 저장하고 공급자 오류 본문·비밀 키는 기록하지 않는다.

이 재시도 제한은 **결제 유예나 접수 마감 정책이 아니다.** stalled가 되어도 Entry를 expired로 바꾸거나 Order.needsReview를 강제로 설정하지 않는다. 나중에 유효한 웹훅이나 수동 조회가 도착하면 기존 정책에 따라 접수를 확정할 수 있다. stalled 이력과 이미 적재한 운영 확인 작업은 보존된다.

## 운영 연결

`.env.example`의 기본값은 다음과 같다.

```text
PAYMENT_RECOVERY_ENABLED=false
PAYMENT_RECOVERY_TOKEN=
```

연결하려면 테스트 DB에 마이그레이션 001~007을 적용하고 토스 테스트 설정을 완료한 다음, 충분히 무작위인 32자 이상의 전용 비밀 토큰을 설정한다. 토큰은 브라우저 코드·공개 저장소·URL 쿼리에 넣지 않는다. 토큰이나 PG가 미설정이면 작업을 실행하지 않는다. 활성화 후 스케줄러가 Authorization 헤더로 Bearer 토큰을 전달하며 위 경로에 빈 JSON 객체를 POST하도록 구성한다.

응답 outcome은 idle, completed, retry_scheduled, stalled, superseded 중 하나다. 주문 ID·계정·결제 참조는 응답에 포함하지 않는다. 응답은 private/no-store다.

이번 작업은 스케줄러가 호출할 실행 경로까지 구현한 것이다. **현재 자동 실행 중인 작업은 없다.** Cloud Run 등 실제 배포 환경에서 주기·동시 실행 수·요청 제한·비밀 관리·모니터링을 정하고 연결해야 한다. 호출당 한 건이므로 마감 직전 규모에 맞는 실행 빈도와 처리량 검증이 필요하다. 운영 확인 outbox 발송·관리자 처리 화면·stalled 재개 기능도 아직 없다.

## 검증

- 전체 테스트 129건 통과. 복구 하위 시나리오 11건.
- PGlite에서 지연 승인 복구, 작업 인스턴스 재시작, 겹치는 실행, 만료 점유 재획득, 오래된 실행 차단, 재시도 소진, 인증·공급자 분리를 검증했다.
- 전체 TypeScript 검사와 해당 파일 ESLint 통과.
- 실제 Next 개발 서버에서 비활성 내부 경로가 503 POLICY_NOT_CONFIGURED와 private/no-store를 반환하는 것을 확인했다.
- 실제 토스·네트워크 PostgreSQL 다중 연결·배포 스케줄러의 실행 및 처리량은 미검증이다.

Claude의 화면 변경은 필요하지 않다. 참가자는 기존 주문·접수 조회를 사용한다. 관리 화면에서 복구 큐를 직접 읽거나 내부 토큰을 사용하면 안 된다. 다음 서버 단계에서 운영 확인 목록과 권한을 별도로 제공할 수 있다.
