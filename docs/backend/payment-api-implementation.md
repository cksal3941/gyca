# 주문·결제 검증·접수 확정 기반

2026-09-15 Codex 구현. 화면·스타일·Claude mock은 수정하지 않았다.

후속 업데이트: 토스 승인·조회 어댑터, confirm 경로, 테스트 전용 설정을 추가했다. 이 문서의 “승인 API/실제 공급자 구현 없음”은 최초 원장 단계의 기록이며, 최신 범위는 [토스 어댑터 구현](toss-adapter-implementation.md)을 따른다. 현재 환경에서는 여전히 비활성이다.

## 구현 범위

| 경로 | 구현 |
| --- | --- |
| `POST /api/v1/entries/{id}/orders` | 본인 제출 건의 참가비 주문 생성·재사용. JSON `{}`, `Idempotency-Key` 필수 |
| `GET /api/v1/orders/{id}` | 본인 주문, 검증된 결제 상태, 운영 확인 필요 여부 조회 |
| `GET /api/v1/orders?cursor=...&limit=20` | 본인 주문 목록, 최대 50개 단위 |
| `POST /api/v1/orders/{id}/reconcile` | JSON `{}`. 공급자 조회로 결제 상태 재확인, 주문당 10초 간격 제한 |
| `POST /api/v1/payments/webhook` | 공급자 어댑터가 검증한 이벤트만 적용. 원문 256 KiB 제한 |

타입은 `src/contracts/payments.ts`, 서버 구현은 `src/server/payments/`에 있다. 마이그레이션은 `005_payments.sql`이다. 실제 DB에는 적용하지 않았다.

**현재 실제 공급자는 null이다.** 신규 주문·외부 결제 확인은 `PAYMENT_UNAVAILABLE`로 차단한다. 테스트는 로컬 시험용 공급자를 사용하며, 토스 샌드박스 결제에 성공했다는 의미가 아니다. 결제창 호출, 승인·취소·환불 API, 자동 재확인 스케줄러, 알림 발송 worker는 아직 없다.

## 주문 규칙

- 금액·통화·결제 기한은 변경 불가능한 제출 스냅샷에서 읽는다. 프런트가 보낸 가격은 받지 않는다. 공모 페이지의 나중 요금 변경은 기존 제출 가격에 영향을 주지 않는다.
- 한 제출에 참가비 주문 한 개만 허용한다. 다른 키로 재요청해도 새 주문을 만들지 않는다. 같은 계정·키를 다른 제출에 쓰면 `IDEMPOTENCY_CONFLICT`다.
- 현재는 `entry_fee`만 구현했다. 본선 참가비, 여러 통화 환산, 재시도용 별도 결제 시도 생성은 미구현이다.
- 주문 생성 후 금액·통화·기한·공급자·가맹점·테스트/라이브 구분·판정 정책은 DB에서도 변경할 수 없다.
- 결제창 연동 전이므로 응답에 결제 시작 액션은 없다. 검증 어댑터가 연결된 경우에만 `check_payment`를 반환한다. 상태가 실패·만료여도 새 주문으로 재결제하지 않는다.

`gyca_competitions.payment_enabled`와 `payment_policy`가 설정되어야 한다. payment_policy 기본값은 null이며, 다음 두 필드가 필요하다.

```json
{ "version": "운영자가 승인한 버전", "approvalBasis": "provider_paid_at" }
```

`approvalBasis`는 `provider_paid_at` 또는 `server_verified_at`이다. 구현은 두 가지를 지원하지만 운영값은 선택하지 않았다. 참가 규정과 결제창 안내에 판정 기준이 일치하는 것을 확인한 후 설정해야 한다.

## 이벤트와 접수 확정

1. 공급자 어댑터는 웹훅 서명 검증 또는 인증된 공급자 조회로 원문을 검증한다. 서명 없는 알림 내용을 그대로 정규화하면 안 된다. 현재 제공되는 것은 인터페이스이며, 실제 공급자의 검증 구현은 없다.
2. 공급자·가맹점·테스트/라이브 구분과 주문, 금액, 통화를 대조한다. 브라우저 성공 페이지·쿼리 파라미터는 결제 증거가 아니다.
3. 이벤트 ID의 중복은 한 번만 반영한다. 같은 이벤트 ID로 다른 내용이 오면 충돌 처리한다.
4. 결제 성공과 접수 확정, 고유 접수번호, 알림 outbox 항목, 이벤트 증거를 같은 DB 트랜잭션으로 저장한다. 실패하면 전부 롤백하므로 공급자의 재전송·재확인으로 복구할 수 있다.
5. 성공한 결제는 나중 실패 이벤트로 되돌리지 않는다. 먼저 실패한 관측 뒤에 검증된 성공이 도착하면 복구한다.
6. 두 번째 결제 성공, 금액·통화 불일치, 다른 주문에 사용된 결제 ID는 증거를 보관하고 `needsReview=true`로 설정한다. 추가 접수번호나 자동 환불은 만들지 않는다.

접수번호는 `GYCA-<UUID>` 형식의 고유 참조값이다. 연속 순번이나 국가·연도 의미는 부여하지 않는다. 이미 발급한 번호와 발급 시각은 DB에서 변경을 차단한다.

`gyca_payment_events`에는 정규화된 증거만 보관하며 수정·삭제를 차단한다. 카드번호나 원문 전체를 저장하는 구조가 아니다. `gyca_payment_outbox`에는 `entry_received`와 `payment_review` 작업만 적재한다. **실제 이메일·메시지는 발송하지 않았다.**

## 마감·지연 처리

- 신규 주문은 스냅샷의 배타적 결제 종료 시각보다 먼저 생성해야 한다.
- `provider_paid_at`: 검증된 공급자 승인 시각이 기한 전이면 알림 수신이 늦어도 접수 확정 가능하다.
- `server_verified_at`: 서버 검증 시각이 기한 전이어야 한다. 늦은 알림의 정상 결제도 운영 확인 대상으로 남을 수 있다.
- 기한과 정확히 같은 시각은 신규 접수 확정 대상이 아니다.
- 기한 밖의 정상 승인은 결제 성공을 숨기지 않는다. 주문은 `succeeded`, 접수는 `submitted`, `needsReview=true`로 남겨 운영 판단을 기다린다. 재결제 버튼은 제공하지 않는다.
- 공급자 승인 시각이 주문 생성보다 앞서거나 서버 현재 시각보다 미래이면 자동 확정하지 않는다. 실운영 전 서버 시계 동기화와 공급자 시각 의미를 확인해야 한다.

환불·철회·보정 정책은 별도 구현 대상이다. 이 단계는 결제 만료를 자동으로 Entry `expired`로 변경하지 않는다. 알림 누락에 대비한 스케줄러는 미연결이며 현재는 인증된 재확인 요청과 공급자 웹훅 재전송으로만 처리한다.

## Claude 연결 안내

- 주문이 존재한다는 사실은 결제 성공이 아니다. `PaymentOrder.state`를 사용하고 `needsReview`가 있으면 운영 확인 중으로 안내한다.
- `submitted` + payment `succeeded`일 수 있다. 접수번호는 EntryDetail의 `received` 응답에서만 표시한다.
- 주문에서 운영 확인이 필요하더라도 이미 정상 확정된 접수번호는 유지된다. 중복 결제 문제와 기존 접수 유효성을 분리한다.
- 프런트가 `state`, `amountMinor`, `paymentKey`, 승인 시각 등을 reconcile 본문에 보내면 422다. 토스용 승인 API는 추후 별도 계약으로 추가한다.
- 일반 EntryDetail 액션은 제출 조회용, 주문의 `allowedActions`는 결제 확인용이다. 결제 시작 UI는 아직 실제 API에 연결하지 않는다.
- 본인 주문 목록 `GET /api/v1/orders`는 화면용 `OrderSummary` 페이지를 반환한다. 공모명·작품명은 제출 당시 동결 스냅샷을 우선 사용하며, 이전 불완전 데이터만 현재 공개 제목 또는 competitionId로 대체한다. 현재 생성 가능한 주문은 `entry_fee`뿐이고 환불 원장이 없어 `refundSummary=null`이다. 단건 `GET /api/v1/orders/{id}`는 결제 진행·폴링용 `PaymentOrder` 계약을 계속 사용한다. 목록 item을 단건 응답으로 파싱하거나 반대로 사용하지 않는다.

## 확인 결과와 한계

- 기존 기능 포함 전체 96건 테스트 통과. 결제 하위 시나리오 21건.
- PGlite PostgreSQL 엔진에서 중복 주문·이벤트, 영수증 중복 방지, 소유권, 가격 위조, 가맹점/환경 분리, 마감 경계·지연, 장애 롤백, 재확인, 목록 분리를 검증했다.
- 실제 Next 개발 서버에서 비로그인 주문 조회 401 및 비활성 웹훅 503 확인.
- 전체 TypeScript 검사, 해당 서버 파일 ESLint 통과.
- 네트워크 PostgreSQL 다중 연결, 실제 토스 웹훅/승인/테스트 결제, 배포, outbox 발송은 미검증이다. 시험용 HMAC 공급자 검증은 토스 서명 규격을 뜻하지 않는다.

토스 검토 결과와 외부 확인 항목은 [토스 해외결제 연동 검토](toss-payment-integration.md)를 따른다.
