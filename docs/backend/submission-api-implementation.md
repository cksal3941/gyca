# 제출·동의 증적 API 구현 현황

2026-09-15. Codex 서버 작업. Claude의 화면·스타일·mock은 수정하지 않았다.

## 구현 범위

- `GET /api/v1/entries/{id}/submission-readiness?locale=en|ko`: 본인 초안의 제출 가능 여부, 필드 오류, 연령그룹, 동의 문서 3종, `policyToken`을 반환한다. locale 기본값은 en이며 요청 언어의 문서가 없으면 제출을 차단한다.
- `POST /api/v1/entries/{id}/submit`: `Idempotency-Key`와 JSON 본문을 받아 제출 내용을 고정한다.
- 기존 본인 단건·목록 조회에서 `submitted` 항목을 읽을 수 있다. 제출 후 부분 저장과 업로드 변경은 차단한다.
- 제출과 증적 저장은 한 트랜잭션이다. 서버가 요청을 검증하는 동안 접수 행과 공모 정책을 잠그며, 동일 키·본문 재전송은 저장된 성공 응답을 반환한다. 마감 후에도 성공한 요청의 재전송은 가능하다.

공통 타입은 `src/contracts/submissions.ts`에 있다. 동의 종류는 `participation_rules`, `privacy`, `work_license`이며 각각 별도로 수락해야 한다.

```json
{
  "revision": 5,
  "locale": "en",
  "policyToken": "GET에서 받은 64자리 토큰",
  "consents": [
    { "kind": "participation_rules", "version": "GET에서 받은 버전", "accepted": true },
    { "kind": "privacy", "version": "GET에서 받은 버전", "accepted": true },
    { "kind": "work_license", "version": "GET에서 받은 버전", "accepted": true }
  ]
}
```

성공 시 `entryStatus=submitted`, 증가한 revision, 서버 `submittedAt`을 반환한다. `receiptNumber`와 `receivedAt`은 null이다. 결제 연결 전이므로 액션은 `view_submission`, 차단 사유는 `PAYMENT_REQUIRED`, `PAYMENT_UNAVAILABLE`이다. 이것은 접수 확정이나 결제 성공이 아니다.

## 화면 연결 규칙 — Claude 전달용

1. 최종 제출 단계에서 readiness를 호출하고 받은 동의 문구를 **일반 텍스트로** 표시한다. HTML로 실행하지 않는다.
2. 제출 버튼의 서버 조건은 readiness의 `allowedActions`에 `submit`이 있는지로 판단한다. 버튼 클릭 전 문서 세 종류의 사용자 수락도 필요하다. 일반 EntryDetail의 액션은 임시저장·조회용이고, 이 단계의 세부 판정은 readiness 응답을 사용한다.
3. 수정·파일 변경 후 readiness를 다시 조회한다. 요청 성공 여부가 불명확할 때 같은 키와 같은 본문으로 재시도한다. 내용을 바꾸면 새 키를 사용한다.
4. `REVISION_CONFLICT`는 초안을 새로 조회한다. `CONSENT_REQUIRED`는 문서를 다시 조회하고 사용자가 변경 내용을 확인하도록 한다. 자동 재동의하지 않는다.
5. 성공 화면은 “제출 완료 · 결제 필요”로 표현한다. 접수번호나 접수 확정 배지를 만들지 않는다. 기존 EntryDetail 조회로 고정된 참가자·작품 내용을 표시할 수 있다. 증적 원본과 저장소 내부 키를 공개하는 API는 제공하지 않는다.

## 서버 검증 및 보관

- 폼 필수 입력, 영문 제목·설명, 분야 선택, 생년월일·거주국, 설정된 연령그룹을 검사한다. 나이는 폼의 기준일에 생일 경계를 적용하여 계산한다. 이름의 영문 필수 여부는 폼 정책을 따른다. 영어 여부를 문자 집합으로 추측하지 않는다.
- 첫 구현은 아트북 제출용이다. 필수 표지 한 개, 최소 20쪽 단일 PDF 정책이 설정되어 있어야 한다. 일반 동영상 공모용 제출 엔진은 아직 아니다.
- 제거되지 않은 파일을 모두 고정한다. 선택 파일도 남아 있다면 검증이 완료되어야 한다. 업로드 중·검증 중·반려 파일은 제거하거나 처리 완료 후 제출한다.
- 서버 검사 결과 `ready`, 저장소 객체 버전, SHA-256, 크기·형식·페이지 수를 확인한다. 클라이언트가 보낸 검증 결과나 제출 시각은 받지 않는다. 기존 파일 검사는 형식 검사이며 악성코드 검사를 대체하지 않는다.
- 참가자·작품·보호자 입력, 공모 정책과 요금, 폼, 파일 버전·체크섬, 동의 문서 원문·언어·버전·해시, 로그인 계정과 동의 시각을 비공개 JSON 스냅샷으로 저장한다.
- DB 트리거가 제출 증적의 UPDATE/DELETE와 제출 후 참가자·작품·보호자 내용 변경을 막는다. 보존기간 경과 후 삭제 절차는 별도 정책·권한 설계가 필요하다.
- `submittedAt`은 잠금 획득 후 서버가 판정에 사용한 시각이다. 트랜잭션 커밋 시각이나 업로드 시작 시각이 아니다. 해당 시각이 배타적 제출 마감보다 이른 경우만 신규 제출이 가능하다. 여러 서버의 시계 동기화와 운영 측 시각 기준 승인이 필요하다.

## 운영 설정 — 기본 비활성

`004_submissions.sql`을 마이그레이션 목록에 추가했다. 실제 DB에는 실행하지 않았다. 신규 `gyca_competitions.submission_policy`의 기본값은 null이며, 이 상태에서는 제출할 수 없다.

승인된 정책을 서버에서 입력할 때 필요한 구조:

- `enabled: true`, 비어 있지 않은 `version`
- `guardianAgeBasis: "submission_date_in_competition_timezone"`
- `guardianAgeByCountry`: 운영자가 승인한 국가 코드별 보호자 확인 기준 연령. 기본 국가·기준 연령은 제공하지 않는다. 미등록 거주국은 차단한다.
- `documents`: 종류·언어 조합이 유일한 문서. 각 문서에 kind, version, locale(en/ko), title, text가 필요하다. 제출 언어의 세 종류가 모두 있어야 한다.
- 기존 공모의 공개·초안 허용·제출기간·폼 정책이 준비되어야 하고, 요금과 결제 마감도 설정되어야 한다. 결제 마감이 제출 마감보다 이르면 제출을 차단한다. PG 활성화는 별도다.

보호자 확인 연령은 참가 부문 연령 기준일과 별개로, 공모 시간대의 제출일에 계산한다. 이 국가별 표는 법률을 자동 판정하는 체계가 아니다. 적용 범위·연령·시간대는 운영 검토 후 설정해야 한다. 테스트의 국가·날짜·연령·문구는 시험용이며 운영 설정이 아니다.

보호자 확인 제공자는 아직 연결하지 않았다. 확인 대상이면 `GUARDIAN_VERIFICATION_REQUIRED`로 차단하며, 사용자 체크박스나 업로드만으로 `verified` 처리하지 않는다. 현재 성공 가능한 경우는 승인된 정책에서 보호자 확인이 필요하지 않은 참가자뿐이다.

마감·유예, 보호자 확인 방식, 파일 한도, 정식 동의 문구 등 미정 정책을 확정한 것으로 처리하지 않았다. 실 DB·저장소·PG 연결도 아직 필요하다.

## 검증 결과

- Node 테스트 74건 통과. 기존 계약·초안·공모·파일 검사를 포함하며 제출 관련 하위 시나리오는 16건이다.
- PGlite PostgreSQL 엔진으로 소유자 분리, 중복 제출, 필수 입력, 파일 검사 상태, 생일 경계, 동의 위조·변경, 마감 경계, 트랜잭션 롤백, 제출 후 변경 금지를 검증했다.
- 실제 Next 개발 서버의 readiness 경로: 비로그인 401, `private, no-store` 확인.
- 전체 TypeScript 검사 및 변경 서버 파일 ESLint 통과. 초기 검사 중 홈 locale 오류가 있었으나 UI 담당 작업 반영 후 재검사에서는 해소되었다.
- 실 PostgreSQL 다중 연결 경쟁, 실제 로그인 쿠키로 제출 성공, 실제 저장소·PG 연결, 배포는 검증하지 않았다.

다음 서버 단계는 제출 스냅샷을 기준으로 주문을 만들고, 검증된 결제 통지만 접수 확정으로 전환하는 결제 기반 구현이다.
