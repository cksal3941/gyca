# 선택한 결제 경로의 주문 고정

2026-09-15. 결제 후보 안내 다음 단계로, 실제 서버의 주문 생성 API에 경로 선택 검증을 연결했다. 실PG·결제창은 여전히 미연결이다.

## Claude 전달: 요청 변경

`GET /api/v1/entries/{id}/payment-options` 후보에 `policyToken`이 추가됐다. 생성 가능한 후보가 있으면 `allowedActions: ["create_order"]`를 반환한다. 이는 주문 생성 허용이며 결제창 실행이나 승인 완료를 뜻하지 않는다. 후보가 없으면 기존처럼 차단한다.

`POST /api/v1/entries/{id}/orders`의 실제 서버 요청은 이제 빈 객체 대신 다음을 요구한다. 기존 `Idempotency-Key` 헤더와 로그인·동일 Origin 규칙은 유지한다.

```json
{
  "routeId": "선택한 후보의 id",
  "policyToken": "선택한 후보의 policyToken",
  "acceptedRefundNotice": true
}
```

`@/contracts/payment-options`의 SelectPaymentRouteSchema를 사용한다. 환불 안내를 보여주고 사용자가 수락한 뒤 보낸다. 금액·국가·가맹점은 보내지 않는다. 성공 응답은 기존 PaymentOrder다. 결제창 시작 액션은 여전히 제공하지 않는다.

정책 원문이 바뀌면 `CONSENT_REQUIRED` 409로 거부한다. 이때 후보와 안내를 다시 읽고 재동의를 받는wkr다. 같은 주문에 다른 경로나 정책 토큰은 `IDEMPOTENCY_CONFLICT` 409다. 네트워크 재시도는 최초 요청의 본문·키를 유지한다. 기존 주문은 최신 정책이 비활성화되어도 동일 요청으로 조회할 수 있지만, 결제 가능 여부는 별도다.

## 서버 보장

- 제출 스냅샷의 거주국·EUR 금액과 선택 경로를 다시 비교한다. 서버에 등록된 공급자의 ID·가맹점·시험/운영 모드가 모두 일치해야 한다.
- 공모전 정책 공유 잠금과 접수 건 잠금 안에서 검증하고 주문을 생성한다. 핵심 주문 서비스의 마감·결제 활성화·멱등성 검사를 그대로 사용한다.
- `gyca_order_routes`에 전체 선택 경로와 환불 안내, 정책 버전·토큰, 동의 계정·시각을 저장한다. 주문 및 증적은 같은 트랜잭션이며 증적 저장 실패 시 주문과 요청 키도 롤백한다. UPDATE/DELETE는 차단한다.
- 주문 공급자는 기존 주문 테이블의 불변 필드다. 실패나 응답 지연을 이유로 다른 공급자로 바꾸지 않는다. 같은 제출의 두 번째 주문도 생성하지 않는다.
- 이전 방식으로 생성되어 경로 증적이 없는 주문에 새 동의를 소급해서 붙이지 않는다. 기존 주문 GET·조회/확인 흐름을 사용한다.

`010_order_routes.sql`을 마이그레이션 목록에 등록했다. 운영 DB 적용은 미실행이다. 오래된 테스트는 결제 원장 자체를 검증하기 위해 내부 기본 생성 경로를 사용한다. 실제 runtime은 경로 입력을 요구하는 생성기를 주입하므로 빈 본문으로 우회할 수 없다.

## 제한과 다음 단계

현재 런타임 공급자는 토스 테스트 하나다. 경로별 주문 생성기는 공급자 목록을 받을 수 있지만, 다중 공급자의 승인·웹훅·복구 분배는 아직 연결하지 않았다. 추가 PG를 실제 서비스에 등록하기 전 이 분배 작업이 필요하다. 실제 결제창, PG 계약, EUR 지원 및 실결제 검증도 남아 있다.

이번 환불 안내 수락 기록은 기존 참가 규정·개인정보·작품 이용허락의 3개 동의를 대체하지 않는다. 보호자 확인과 보존기간 만료 삭제 절차도 별도 미완료다.

## 검증

경로 선택·원장·복구 테스트 52개 통과. 주문 1개 유지, 변경 정책·잘못된 국가·미설정 공급자·다른 소유자 거부, 증적 불변성, 증적 실패 시 주문 롤백, HTTP의 빈 요청·미동의·금액 추가 거부를 확인했다. 타입 검사와 변경 파일 ESLint 통과. PGlite를 사용했으며 실제 PostgreSQL 다중 연결·실PG 검증은 아니다.
